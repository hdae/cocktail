# 0003. KV キャッシュを fp16 に戻し iSWA コンパクトキャッシュで n_ctx 32768 へ

- Status: Accepted
- Date: 2026-07-02
- Scope: `apps/server` の LLM ロード構成（`config.py`, `services/llm.py`, `main.py`,
  `.env.example`）
- 前提: [0002](0002-phase2-agent-loop.md)（エージェントループ。n_ctx 16384 + q8_0 KV を導入）

## Context

0002 の実装時、16GB VRAM に長文脈を収めるため既定を `n_ctx=16384 + q8_0 KV +
flash_attn` とした。その後の実運用（多ターン・~16k 文脈）でユーザーが以下を観測した:

- 文脈が伸びるほど指示追従性が低下する
- ツール呼び出しが不安定になり、本文（会話テキスト）が表示されないターンが多発する

当時の採否ゲートは VRAM とシングルターンの decode 速度のみで、多ターン品質に対して
構造的に盲目だった。ユーザー要望は「fp16 で行けるところまで n_ctx を増やす」。

## 実測（gemma-4-12B heretic Q4_K_M / RTX 5070 Ti 16GB / WSL2 / llama-cpp-python 0.3.32）

### fp16 KV の VRAM フィージビリティ

WSL2 では Windows ホストも同じ VRAM を共有する（計測時ホスト ~2.5-3GB）。溢れは
CUDA OOM ではなく WDDM 共有メモリへのスピル（decode が桁で崩れる）として現れる。

| 構成 | プロセス増分 | decode | 判定 |
| --- | --- | --- | --- |
| f16 KV, SWA フル, 16384 | +12.3GB | 1.7 tok/s | スピルで実用不可 |
| f16 KV, SWA フル, 12288 | +11.0GB | 57.9 tok/s | 可 |
| f16 KV, `swa_full=False`, 16384 | +8.5GB | 71.7 tok/s | 可 |
| **f16 KV, `swa_full=False`, 32768** | **+8.8GB** | **71.7 tok/s** | **採用** |

Gemma 4 は iSWA（大半の層がスライディングウィンドウ注意）で、llama.cpp 既定は SWA 層
にも n_ctx 全長の KV を確保する（`swa_full=true` 相当）。`swa_full=False` で SWA 層の
KV をウィンドウ長に切り詰めると、全注意層だけが n_ctx に比例するため 32768 でも
+8.8GB に収まり、KV 読み量が減って decode も速くなる（58→72 tok/s）。

### `swa_full=False` の正しさ（greedy 一致検証）

- fresh 同士の再現: 一致
- swa_true vs swa_false: 本文+ツール呼び出し冒頭（200 字超）完全一致。後半で 1 トークン
  揺れ得るが、これは FP 演算順差による近接タイの反転で、バッチ prefill と逐次 decode の
  間に既存する非決定性と同クラス（注意のセマンティクスは構成上同一）
- 毎ターンの `[Turn N / current]` 書き換え相当の末尾分岐: キャッシュ再利用ありと fresh が
  一致し、部分再利用も効く（2.1s vs 4.9s）
- 深い分岐（会話ブランチ相当）: llama-cpp-python が部分 KV 削除不可を検知して全文再評価に
  正しくフォールバックする（`Llama.generate` が `kv_cache_seq_rm` の戻り値を確認する実装
  を確認済み）。品質差なし、レイテンシのみ

### fp16 vs q8_0 の同一条件 A/B（回帰仮説の検証）

固定スクリプト履歴（画像生成主体 64 ペア）を深さ 4 段階（4.5k/8.6k/13.1k/17.9k tokens）で
カットし、同一シード 3 種 × プローブで両 KV 型を比較（n_ctx=32768, swa_full=False）。

直接生成プローブ（新規絵の指示追従 / 純チャット+2個前参照 / seed keep 指示）:

| | f16 | q8_0 |
| --- | --- | --- |
| 全チェック pass | 28/36 | 33/36 |
| 本文欠落 | 0 | 0 |
| ツール呼び出し破綻 | 0 | 0 |

エージェントループ経由プローブ（search_tags 必須のキャラ依頼、本番 `run_turn` 使用）:

| | f16 | q8_0 |
| --- | --- | --- |
| 全チェック pass | 20/24 | 18/24 |
| 検索スキップ（知ったかぶり） | 3（全て最深部） | 6（中深部から） |

**q8_0 犯人説は支持されない**: 主要な失敗（「2個前」の参照解決誤り、深部での検索指示
無視）は両アームで同様に起き、深さそのものが駆動している。q8_0 は検索指示の減衰が
やや早い傾向（中深部 3/6 vs 6/6）があるが標本が小さく、確証ではない。観測された回帰の
実体は「n_ctx 拡大で会話が深くなり、深さ由来の追従劣化が顕在化した」が最有力。

## Decision

既定を **`llm_kv_cache_type="f16"` + `llm_swa_full=False` + `llm_n_ctx=32768`** にする。

- fp16 復帰はユーザー要望であり、iSWA コンパクト化で VRAM コストが消えた今、量子化 KV を
  既定に残す理由がない（decode も高速化）。機械プローブで拾えない主観品質への
  q8_0 の寄与も変数ごと排除できる
- `swa_full` は上流パラメータ名をそのまま config に出す（発見可能性優先）
- q8_0 / q4_0 は 32k 超の文脈が要るときの明示オプトインとして残す

## Consequences

- プロセス ~8.8GB となり、ホスト変動（~3GB）込みでも余裕 ~4GB。将来の vision
  (mmproj) / embedding 常駐の予算が確保された
- 深い履歴分岐（ブランチ切替）は全文再プレフィル（~18k で 5 秒前後）になる
- 回帰の根本原因は KV 型ではなく深さ由来の追従劣化。構造対策としてターン冒頭の
  ベクトル事前検索注入（ユーザー案）を次フェーズで設計する（別 ADR）
- 残課題（既知・未対応）: ①深部で自信のあるキャラを検索せず非正規タグ
  （例: `texas, arknights`）を書く ②検索成功後のホップで会話文を書かずツールへ直行し
  本文が空になるケースが稀にある（48 回中 1 回） ③search_tags の結果要約が
  アンダースコア付き正規形を返すため、モデルがそれを positive にそのまま写し
  「スペース区切り」の表記規約と衝突する
