# 0005. 事前検索によるタグ候補注入（Stage 1: 辞書照合）

- Status: Accepted
- Date: 2026-07-03
- Scope: `apps/server` のタグ逆引き（`services/tags.py` `match_in_text`）と
  ターン開始時の候補注入（`services/llm.py` `_lookup_tag_hints`,
  `services/prompt_builder.py` `build_user_message` / `display_tag`, `config.py`
  `llm_tag_hints`）
- 前提: [0002](0002-phase2-agent-loop.md)（search_tags とエージェントループ）、
  [0003](0003-kv-cache-fp16-iswa.md)（深さ由来の追従劣化の実測）、
  [0001](0001-llm-conversation-harness.md)（埋め込み検索の保留判断）

## Context

search_tags のエージェントループ（0002）は「検索が発火すれば結果は的確に使われる」一方、
発火自体はモデルの自発判断に依存する。実測で確認済みの失敗は 3 種:

1. **知ったかぶり**: 知っているつもりのキャラで検索せず、非正規タグ
   （`texas, arknights` 等）のまま生成する。
2. **深さ由来の検索規律低下**: 0003 の A/B で、文脈 18k では検索指示が両アームで消滅
   （texas 級 0/3）。プロンプト補強（`0694045`、再評価で維持確定）でも残る構造問題。
3. **残る非収束の尾**: 再評価で ~2/12 が検索後 generate まで到達しない。

いずれも固有名詞（キャラ/シリーズ）で起きる。実 CSV（hdae 162,840 行）を確認したところ、
問題を起こした固有名詞は全て日本語 alias を持つ（`ホシノ`→`hoshino_(blue_archive)`、
`テキサス`→`texas_(arknights)`、`花火`→`fireworks`/`sparkle_(honkai:_star_rail)` 両義）。
つまり「発話中の語を alias 辞書と突き合わせる」だけで、確認済みの失敗クラスは
モデルの判断を経由せずに候補を供給できる。

併発の隣接課題: 検索要約が CSV 正規形（アンダースコア付き）をそのまま返し、モデルが
positive へ写して「lowercase, spaces, no underscores」規約と衝突していた。

## Decision

**ユーザ発話の事前検索→候補注入を導入する。検索器は段階構成**（ユーザ決定）:

1. **Stage 1（本 ADR・実装済み）= 辞書照合**。`TagIndex.match_in_text` が発話文を
   sliding window の最左最長一致で走査し、tag/alias 完全一致の行を post_count 降順で
   返す（上限 8 件）。
   - 1 文字キーは照合対象外（日本語文で無差別に当たるノイズ源）。
   - ASCII キーは単語境界を要求（`miku` を `mikura` に当てない）。CJK は境界なし。
   - 最長一致優先: `花火大会` は aerial_fireworks だけに当たり内側の `花火` を拾わない。
   - 曖昧キー（`花火` = fireworks / sparkle）は全行を候補に返し、文脈選択はモデルに
     委ねる（role:tool 候補からの採用が的確という 0002 の実測からの類推）。
   - **カテゴリの絞り込み・優遇はしない**（DECIDED: ユーザ判断。artist 候補等が邪魔に
     なったらそのとき除外を検討）。
2. **注入は current ターン限定の turn-local**。`run_turn` 開始時に逆引きし、current の
   user メッセージ末尾に `(auto tag lookup — …: 候補)` ブロックを添付する。一時
   `messages` のみで永続履歴・SSE・型に出ない（0002 案A と同じ封じ込め）。過去ターンの
   replay には残さない（文脈の恒久肥大と「当時見た内容との乖離」を避ける）。
   - ヒット無しならブロック自体を出さない = 雑談ターンを汚さない自然なゲート。
   - 生成誘発を防ぐため「generate_image を呼ぶときだけ使う」条件を文面に含める。
   - 合成 search_tags 往復としての偽装注入は不採用: モデルが取っていない行動の捏造
     replay（0001 の模倣ドリフトの教訓と同型）+ 雑談ターンへの生成バイアスが強い。
3. **提示形の正規化を 1 経路に集約**（`display_tag`: `_`→空白）。注入候補と検索要約
   （`_summarize_tags`）の双方が通り、隣接課題を解消する。
4. **`LLM_TAG_HINTS`（既定 ON）** を A/B・切り分け用 kill-switch として置く。
5. **search_tags ツールは併存**。system 指針に「候補が付いていればそれを使い、検索は
   候補に無い・足りない要素だけ」を追記し、無駄ホップを減らす。

### Stage 2（未着手・別途提案）= ベクトル検索の追加

言い換え・情景語（辞書に載らない表現）のカバーとして、同じ注入インタフェースの裏に
ベクトル検索器を追加する。0001 の保留判断（booru 語彙への構造的不適合）は温存し、
**採否ゲート**（日本語情景クエリ 20-30 本の hit@k + 雑談/コントロール非回帰）を通過した
場合のみ採用する。埋め込みモデルは EmbeddingGemma 300m を仮置きとするが、**着手時に
より適切な多言語検索特化モデルが無いか再調査してから決める**（ユーザ指示）。

## Consequences

- **実機ゲート合格**（固有名詞 3 + control + タグ語入り雑談 2 × 4 シード = 24 駆動）:
  注入発火 24/24、生成到達時の採用タグは全件正規形（スペース区切り）、検索ホップ 0/16
  （候補が足りる依頼では検索が不要になった）、雑談 8/8 で誤生成・誤検索ゼロ、本文 24/24。
- **ゲート 1 巡目が露出した穴と是正**: 反停止命令（`0694045`）が search_tags 節にしか
  無く、注入で検索が不要になるとほぼ全ターンが命令の無い直接生成経路に乗り、「ちょっと
  待ってて」と宣言だけでツールを呼ばず止まる既知の尾が顕在化した（画像プローブ生成
  11/16。ベースラインでも直接経路の収束率は 3/5 と検索経路 10/11 より低く、注入が
  壊したのではなく命令の穴へトラフィックが移った）。命令を CALL IT 節へ一般化して
  経路非依存にし、再ゲートで生成 15/16（ベースライン 13/16 以上）・雑談 8/8 維持。
- 残る尾（texas 1/4 の宣言止まり）はモデル能力の確率的な尾。さらなる構造対策は
  forced `tool_choice` 2 パス（0001 記載・バックログ）。
- 逆引き辞書は `TagIndex` 構築時に既存 norm 文字列を共有して作る（追加メモリは dict
  構造ぶん、実 CSV で数十 MB 級の CPU RAM）。照合は O(発話長 × 最長キー長) のハッシュ
  照合でサブ ms。
- **有効性は CSV の alias 収録率という実装データ依存**（仕様保証ではない）。未収録の
  愛称・言い換えは拾えない — Stage 2 の動機。
- ひらがな⇔カタカナの読み違い（`ほしの` 等）は正規化で吸収しない（主要タグはひらがな
  alias を CSV 側が持つ。折り畳み正規化は衝突面を広げるため、実害が出てから検討）。
- 注入ブロックはプロンプト実装挙動への依存が無いプレーンテキストで、#2232 マージ後の
  構造化 tool_calls 移行（0001/0004 の撤去トリガ）とも独立に生き残る。
